# 24 权限请求与降级体验方法论

## 这份手册解决什么问题

移动端权限不是“启动时一次性申请”。过早、过多、无解释的权限弹窗会降低授权率，也可能影响平台审核。拒绝、永久拒绝、iOS limited、Android 版本差异都要被设计。

这份手册用于设计相册、相机、通知、麦克风等权限请求和降级体验。

## 什么时候使用

- 适合：相机、相册、通知、麦克风、定位、保存相册、分享文件。
- 不适合：不触发系统权限的普通 UI 状态。

## 一句话原则

权限要在用户理解价值的场景里请求，并且拒绝后仍有可走的路。

## 决策表

| 场景 | 做法 | 原因 |
| --- | --- | --- |
| 首次进入 App | 不直接连环请求 | 用户还不知道价值 |
| 用户点击选图 | 请求相册/相机权限 | 场景明确 |
| 系统弹窗前 | 先做权限预热说明 | 提高信任 |
| 用户拒绝 | 给替代路径或重试入口 | 拒绝不是死路 |
| 永久拒绝 | 引导去设置 | App 不能再弹系统框 |
| iOS limited | 展示部分授权状态 | 不能当完整授权 |
| 保存到相册失败 | 区分权限、文件、系统错误 | 给可执行反馈 |
| 通知权限 | 在用户触发订阅/提醒后问 | 避免空泛请求 |

## 固定检查问题

```text
用户现在是否理解为什么需要这个权限？
拒绝后核心功能是否还能降级使用？
永久拒绝时是否有设置入口？
iOS limited 和 Android 版本差异是否单独处理？
权限文案是否进入多语言？
```

## Flutter 实现拆分

```text
Permission pre-prompt UI
  解释为什么需要权限。

Permission service
  封装 permission_handler / photo_manager。

Feature handler
  根据权限结果执行选图、拍照、保存、录音。

UI state
  展示未询问、授权、部分授权、拒绝、永久拒绝、失败。
```

## 常见坏味道

- App 启动立即请求相机、相册、通知。
- 把 denied、permanentlyDenied、limited 当成同一种。
- 权限拒绝后只 toast “失败”。
- 缺少 iOS `Info.plist` 或 Android Manifest 声明。
- 系统权限文案和 App 内说明不一致。
- 保存相册失败时不知道是权限还是文件错误。

## 验收标准

- 首次请求发生在明确用户动作后。
- 拒绝、永久拒绝、limited 都有不同 UI 和下一步。
- 真机验证 iOS/Android 关键路径。
- 权限文案进入 `.arb`，长文案不挤爆 UI。
- 保存/选择失败有可执行操作：重试、去设置、换文件。
