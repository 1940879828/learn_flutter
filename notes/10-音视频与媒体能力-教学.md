## 本章教学闭环

媒体能力不要从插件名开始学，要从生命周期开始学。

```text
媒体来源：asset / network / file
→ 创建控制器
→ initialize
→ ready
→ play / pause
→ 页面不可见或销毁
→ dispose
```

Web 前端可以类比：

- `Image.network` 像 `<img src="https://...">`，但 Flutter 需要你显式考虑缓存和错误占位。
- `video_player` 像 `<video>`，但 controller 是你自己管理的资源对象。
- 页面离开、列表滚动、App 进入后台，相当于 Web 的 visibility/change + component unmount，但移动端资源成本更高。
- `file` 来源对应用户选择、下载或生成后的本地文件，不等于系统相册永久可访问。

## 第 1 步：先分清媒体来源

常见来源有三种：

- `asset`
- `network`
- `file`

你要先知道媒体来自哪里，后面控制器和缓存才好设计。

## 第 2 步：理解视频控制器生命周期

视频类对象一般都需要：

- 初始化
- 播放
- 暂停
- 释放

如果不 `dispose`，很容易留下资源问题。

## 第 3 步：理解图片和视频的差别

图片更多是展示和缓存。
视频除了展示，还要考虑时长、进度、暂停、音轨、后台状态。

所以视频链路通常比图片复杂一截。

## 第 4 步：音频要先做能力预研

如果目标项目后面加音频，先判断它属于哪类：

- 短音效
- 长音频播放
- 录音
- 音视频混合

不同场景，插件和平台配置都不同。

## 第 5 步：做一个媒体实验页

建议练：

- 一个 asset 图片
- 一个本地选图预览
- 一个远程视频播放
- 一个页面离开释放 controller

本项目先做生命周期模拟版：

- `MediaSourceKind` 展示 asset/network/file 的来源差异。
- 图片预览用内存图片模拟 asset/file 两种语义，不请求相册。
- `FakeVideoController` 用日志展示 `initialize()`、`play()`、`pause()`、`dispose()`。
- 页面 `dispose()` 里释放 controller，训练“资源对象必须释放”的习惯。

等进入真实项目或专门媒体实验时，再引入 `video_player`，并补真机/模拟器验证。

## QA 问答

### Q1：为什么视频一定要管 `dispose`？
因为底层解码器和平台通道是资源型对象，不释放容易泄漏。

### Q2：`photo_manager` 和 `image_picker` 怎么分工？
一个偏相册管理，一个偏快速选取。

### Q3：音频为什么要单独预研？
因为它涉及后台、焦点、编码和权限，跟图片展示完全不是一个复杂度。

### Q4：媒体失败后应该怎么提示？
要区分权限问题、网络问题、格式问题、初始化失败。

### Q5：为什么目标项目里视频比音频更突出？
因为它的业务主线更靠近图片转视频和媒体生成。
