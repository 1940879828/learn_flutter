# 20 路由与页面流设计方法论

## 这份手册解决什么问题

Flutter 的路由不只是“跳页面”。同一个按钮到底用 `go`、`push`、`replace` 还是 `pushReplacement`，会影响返回栈、登录回跳、参数恢复、deep link 和页面生命周期。

这份手册用于设计页面流时，先决定用户路径和返回语义，再写跳转代码。

## 什么时候使用

- 适合：新增页面、登录拦截、创建/选择/裁剪流程、详情页、搜索页、引导页完成跳转。
- 不适合：页面内 tab 或局部展开，不需要改变路由栈的交互。

## 一句话原则

先写清“用户按返回键应该去哪里”，再选择路由 API。

## 决策表

| 场景 | 选择 | 原因 |
| --- | --- | --- |
| 列表进详情 | `push` | 保留列表，返回自然 |
| 创建页/选择器返回结果 | `push<T>` + `pop(result)` | 上一页等待结果 |
| 搜索词、筛选、tab 可由 URL 表达 | `go` + query | 状态可恢复、可分享 |
| 登录后不想回到登录页 | `pushReplacement` | 替换中间页，保留下层业务栈 |
| 引导完成进入主流程 | `go` 或集中封装 | 清理引导路径，避免返回引导 |
| 同一页面换 id 或 location | `replace` | 保留页面形态，原地更新 |
| 登录态/权限态变化触发守卫 | redirect / refresh | 路由层统一判断 |
| 临时内存对象 | `extra` | 只适合一次跳转，不适合恢复 |

## 固定检查问题

```text
这个页面是否应该出现在返回栈里？
参数是资源身份、可选状态，还是一次性内存对象？
用户从 deep link 进入时是否能恢复？
登录/权限失败后应该回到哪里？
完成流程后返回键应该回上一页、首页，还是退出流程？
```

## Flutter 实现拆分

```text
route constants
  统一声明 path、name、参数生成方式。

router config
  统一声明 GoRoute、redirect、page builder。

page entry
  读取 path/query/extra，做参数校验和兜底。

flow action
  用封装好的 PageKeys / Pages.toXxx 发起跳转。
```

## 常见坏味道

- 手拼路径散落在多个 Widget 里。
- `extra` 里传关键数据，但 deep link 或进程恢复后丢失。
- 登录页完成后直接 `push` 详情，导致返回又回到登录页。
- 返回值本该 `pop(result)`，却用全局状态绕一圈。
- 页面参数没有兜底，缺 query 或 extra 就崩。
- 在 `go_router` 项目里随意混用全局 `Navigator.push`。

## 验收标准

- 能画出目标页面的进入、返回、取消、完成路径。
- path 参数表达资源身份，query 表达可选状态，extra 只传短命对象。
- 登录/权限 redirect 不产生错误返回栈。
- 手工验证进入、返回、刷新、缺参和完成流程。
