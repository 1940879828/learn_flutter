# 27 登录与账号状态方法论

## 这份手册解决什么问题

Firebase 登录成功不等于业务登录成功。真实 App 还要处理第三方 provider、Firebase credential、ID token、后端用户创建、token 刷新、auth state 广播、退出登录和失败恢复。

这份手册用于设计登录与账号状态链路，避免 Firebase 用户和业务用户状态分裂。

## 什么时候使用

- 适合：登录页、账号恢复、退出登录、token retry、后端用户同步、登录拦截。
- 不适合：只展示静态用户昵称或头像，不改变账号状态。

## 一句话原则

登录链路必须同时满足认证成功、业务用户同步成功、UI 状态一致。

## 决策表

| 状态 | 处理 | 原因 |
| --- | --- | --- |
| 用户未登录 | 展示登录入口 | 可继续浏览则不强拦 |
| provider 登录中 | 禁用重复点击 | 避免多次拉起 SDK |
| 用户取消 | 回到未登录，不报错 | 取消是正常路径 |
| provider 失败 | 展示供应商错误 | 和后端失败分开 |
| Firebase 成功 | 获取 ID token | 后端需要验证 |
| 后端用户创建失败 | 退出 Firebase 或回滚 | 避免状态分裂 |
| 401/403 | 强刷 token 重试一次 | 处理 token 过期 |
| 退出登录 | 清理账号相关状态 | 避免残留用户数据 |

## 固定检查问题

```text
当前 UI 依赖的是 Firebase user，还是业务 user？
后端用户创建失败时如何回滚？
登录成功由按钮回调驱动，还是 auth state stream 驱动？
token 过期后在哪里统一刷新？
退出登录后哪些本地状态必须清理？
```

## Flutter 实现拆分

```text
Auth service
  负责 provider SDK、Firebase credential、signOut。

Backend account repository
  负责 create/sync/get current user。

Auth state provider
  广播登录态、业务用户、金币、VIP 等账号状态。

Login page
  展示登录入口、loading、取消、错误。

Route guard
  按登录态控制进入或回跳。
```

## 常见坏味道

- Firebase 成功后不检查后端用户是否创建成功。
- 登录失败时 Firebase 用户残留。
- 完整 ID token 打印到日志或 UI。
- 登录按钮可重复点击。
- 退出登录只清 Firebase，不清业务缓存。
- 每个 API 自己处理 401/403，策略分散。

## 验收标准

- 能画出 provider -> Firebase -> backend user -> UI state 全链路。
- 取消、供应商失败、后端失败有不同反馈。
- 后端失败不会留下“看似已登录”的 Firebase 状态。
- token 只在请求头使用，不进入日志和源码。
- 登录页监听统一 auth state，而不是只相信按钮回调。
