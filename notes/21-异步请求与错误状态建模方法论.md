# 21 异步请求与错误状态建模方法论

## 这份手册解决什么问题

真实页面的异步请求不只是 loading 和 data。用户取消、网络超时、鉴权失败、服务端错误、空结果、旧请求回包、页面退出后 setState，都需要被建模。

这份手册用于设计异步页面状态，避免把错误都塞给 UI 临时判断。

## 什么时候使用

- 适合：列表、详情、生成任务、登录、上传、下载、轮询、搜索。
- 不适合：纯本地同步计算或不需要用户反馈的内部小函数。

## 一句话原则

异步状态要表达用户能感知的过程，而不是只表达代码是否正在 await。

## 决策表

| 场景 | 状态模型 | 原因 |
| --- | --- | --- |
| 首次加载 | `loading` | 需要首屏反馈 |
| 有旧数据时刷新 | `stale + refreshing` | 保留旧内容，避免闪空 |
| 无数据成功 | `empty` | 空结果不是错误 |
| 请求失败 | `error + retry` | 用户需要知道下一步 |
| 用户主动取消 | `canceled` | 取消不是失败 |
| 搜索输入变化 | request id / cancel | 丢弃旧请求结果 |
| 页面退出 | dispose cancel | 避免更新已销毁 UI |
| 鉴权失败 | refresh token / relogin | 和普通网络错误分开 |

## 固定检查问题

```text
请求是一次性、持续流，还是轮询？
失败分网络、超时、取消、未授权、业务错误吗？
有旧数据时刷新是否要保留旧画面？
重复点击或连续搜索会不会旧结果覆盖新结果？
页面退出后异步结果怎么处理？
```

## Flutter 实现拆分

```text
UI
  根据状态展示 loading、empty、error、data、retry。

AsyncNotifier / FutureProvider
  管理异步状态、刷新、重试和取消语义。

Repository
  把 DioException / SDK error 转成业务错误。

ApiClient
  处理请求、header、timeout、interceptor、cancel token。
```

## 常见坏味道

- 只有 `isLoading`，没有错误类型和空状态。
- `build()` 里创建 `Future`，导致重复请求。
- catch 后只打印日志，UI 永远停在 loading。
- 刷新时清空旧数据，页面闪烁。
- 搜索旧请求后返回，覆盖最新搜索结果。
- 页面 dispose 后异步回调继续 setState。

## 验收标准

- 每个用户可见状态都有 UI。
- 失败可以恢复，重试路径清晰。
- 取消、超时、未授权、业务失败不会混成同一文案。
- 连续请求不会旧结果覆盖新结果。
- focused test 覆盖成功、失败、空结果和重试。
