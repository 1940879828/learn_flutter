# 17 引导页设计与制作方法论

## 本章定位

这不是“怎么做几张欢迎页”的教程，而是写任何 onboarding 之前先看的决策手册。

引导页的本质不是教用户背功能，而是把用户从陌生状态带到第一次相信这个产品有用的状态。真正要设计的是一条新用户路径：用户为什么来、第一次应该做什么、在哪里感到产品有价值、哪些信息必须提前说、哪些提示可以等用户走到场景里再出现。

## 一句话原则

先定义用户的“第一次成功”，再决定要不要做前置引导页。

如果用户一进 App 就能理解并开始操作，前置引导越少越好；如果产品价值、交互方式、权限原因或个性化配置需要提前解释，再设计 onboarding。很多时候，空状态、上下文提示和首次任务，比连续几页介绍卡片更有效。

## 开始前的 6 行 Brief

每次准备做引导页前，先填这 6 行：

```text
目标用户：
用户第一次打开时的动机：
用户的第一次成功动作：
必须提前解释的信息：
可以延后到使用中提示的信息：
完成引导后要把用户带到哪里：
```

这 6 行填不清楚时，不要急着画页面。否则很容易做成“功能 1、功能 2、功能 3”的宣传页，但用户看完仍然不知道下一步该做什么。

## 先判断是否需要引导

### 不一定需要完整引导的情况

- App 使用的是用户熟悉的标准模式，例如普通列表、搜索、设置、详情页。
- 用户打开 App 时目标很明确，例如查信息、拍照、提交任务、查看消息。
- 首屏本身已经能让用户直接开始核心动作。
- 需要解释的内容可以放在空状态、按钮旁提示、工具提示或帮助入口里。

这种场景优先让用户直接进入产品，在需要帮助的位置给提示。

### 更适合做引导的情况

- 产品有陌生交互，例如 AI 生成、复杂编辑器、游戏操作、创作工作流。
- 用户必须先授权相机、相册、通知、麦克风、定位等权限。
- 产品需要先收集偏好，才能给出有用推荐。
- 用户第一次成功路径较长，需要分步骤降低压力。
- 业务上确实需要解释价值、建立信任或完成账号状态初始化。

这种场景可以做 onboarding，但仍然要短、可跳过、可恢复、能落到真实动作。

## 主流引导类型

### 1. 价值说明型

用 2-3 页告诉用户产品能帮他得到什么结果。

适合：轻量工具、内容消费、创作类产品的首次价值解释。

注意：不要写功能清单，要写用户收益。

```text
差：支持 AI 拼写、语法检查、多语言翻译。
好：写完一句话，立刻得到更自然的英文表达。
```

### 2. 个性化选择型

询问用户目标、偏好、水平、使用场景，用来定制后续体验。

适合：学习、健身、内容推荐、AI 创作、效率工具。

注意：每个问题都要能解释“为什么现在问”。如果这个信息不能立刻改善体验，就延后收集。

### 3. 权限预热型

在系统权限弹窗前，先说明为什么需要权限、开启后用户能得到什么、拒绝后还能不能继续用。

适合：相机、相册、通知、麦克风、定位、通讯录等敏感权限。

注意：不要一启动就连续弹系统权限。先让用户理解场景，再触发系统弹窗。

### 4. 交互教学型

让用户在低风险环境里实际操作一次，而不是只看说明。

适合：游戏、编辑器、复杂手势、AI 工作流、地图/画布/音视频工具。

注意：它应该像练习关卡，不像考试。每一步只教当前动作，不要求用户记住后面才会用的内容。

### 5. 渐进式引导

用户走到某个功能附近，或者第一次触发某个行为时，再显示提示。

适合：功能较多、路径较长、专业工具、频繁迭代的 App。

注意：提示必须容易关闭，也要能重新找到。不要解释齿轮、返回、分享这类标准图标。

### 6. 空状态引导

当列表、项目、历史记录、生成结果为空时，把空状态变成下一步入口。

适合：任务列表、作品库、聊天历史、生成记录、收藏夹。

注意：空状态最好提供一个明确按钮，而不是只展示“暂无数据”。

### 7. 清单型引导

给用户 2-5 个激活任务，例如创建第一个项目、导入素材、生成一次结果、保存作品。

适合：SaaS、复杂工具、创作平台、需要多步激活的产品。

注意：任务必须通向真实价值，不要把“看完教程”当成任务本身。

## 选型决策表

| 场景 | 优先引导方式 |
| --- | --- |
| 用户一进来就知道怎么用 | 少做前置引导，直接进产品 |
| 产品价值需要解释 | 价值说明型，控制在 2-3 页 |
| 需要偏好才能推荐内容 | 个性化选择型 |
| 需要敏感权限 | 权限预热型 |
| 交互方式陌生 | 交互教学型 |
| 功能多、路径长 | 清单型 + 渐进式引导 |
| 数据为空时用户不知道干什么 | 空状态引导 |
| 老用户需要了解新功能 | 可关闭、可回看的上下文提示 |

## 页面内容结构

一个常见且稳妥的 onboarding 结构：

```text
第 1 屏：告诉用户会得到什么结果。
第 2 屏：解释这个结果为什么轻松、可信、适合他。
第 3 屏：让用户做一个低成本选择或动作。
最后：进入第一次成功动作。
```

设计每一屏时，用这个检查：

- 这一屏只讲一个概念吗？
- 用户看完知道下一步要做什么吗？
- 这句话是用户收益，还是内部功能名？
- 这条信息真的必须现在出现吗？
- 用户能跳过吗？
- 完成后会落到真实任务，而不是普通首页发呆吗？

## 交互原则

- 必须可跳过，尤其是价值说明型和教学型引导。
- 每一屏只讲一个概念，避免一屏塞满功能点。
- 不要求用户记忆后面才会用的信息。
- 不解释标准 UI 常识，把解释留给陌生概念和关键风险。
- 权限请求要有预热，不要连续触发系统弹窗。
- 引导完成后，要进入一个明确动作，例如创建任务、生成作品、选择模板、打开编辑器。
- 已完成状态要持久化，但要留出重看入口，例如设置页、帮助页或新功能提示入口。
- 引导内容要支持多语言，文案不要写死在复杂业务逻辑里。

## Flutter 技术实现模型

普通前置引导可以拆成这些职责：

```text
OnboardingRoute
  判断是否需要展示引导，决定进入 onboarding 还是首页。

OnboardingPage
  页面容器，处理 PageView、PageController、跳过、下一步、完成。

OnboardingStep
  每一步的数据模型，包含标题、描述、图片/动画、按钮文案、行为类型。

OnboardingState
  记录当前步骤、用户选择、loading、error、是否完成。

Persistence
  本地保存 hasCompletedOnboarding、版本号、用户偏好等。

Analytics
  记录展示、下一步、跳过、完成、每一步流失。

PostOnboardingAction
  完成后跳转到首页、登录、权限请求、创建第一个任务或模板选择。
```

最小实现通常是：

```text
PageView + PageController + 页面指示器 + 跳过按钮 + 完成按钮 + 本地持久化
```

如果引导只是几页静态说明，`StatefulWidget` 就够了。如果涉及账号、权限、远程配置、个性化问答、埋点、实验分组，状态和副作用应下沉到 provider、VM 或 handler，不要全部塞进 Widget 的 `build` 方法。

## Flutter 代码组织建议

在 Flutter 项目里可以按 feature-first 放置：

```text
lib/ui/pages/onboarding/
  onboarding_page.dart
  onboarding_step.dart
  onboarding_provider.dart
  widgets/
    onboarding_step_view.dart
    onboarding_progress_indicator.dart
```

共享层只放稳定能力：

```text
lib/engine/persistence/
  onboarding_preferences.dart

lib/routing/
  router.dart
```

不要因为样式像轮播，就直接抽成全局组件。只有当多个业务域都需要同一套语义和行为时，再抽公共 Widget。

## 和 Web 前端的迁移类比

| Flutter | Nuxt/Next 类比 |
| --- | --- |
| `OnboardingRoute` | middleware / route guard |
| `PageView` | carousel / stepper |
| `PageController` | controlled component state |
| `SharedPreferences` | localStorage / cookie |
| Riverpod provider | composable / store |
| `go_router` redirect | router middleware redirect |
| permission pre-prompt | 浏览器权限弹窗前的自定义解释 UI |
| empty state | 首次进入 dashboard 的空数据引导 |

核心差异是：Flutter 的权限、生命周期、页面恢复、动画性能和平台差异更明显，所以引导页不能只按 Web 的“组件 + localStorage”思路做，还要考虑 App 冷启动、返回栈、系统权限弹窗和多端尺寸。

## 面向 AI/创作类 App 的特别提醒

如果产品类似 SpellAI、图片/视频生成、AI 写作或创作工具，好的引导通常不是“展示模型能力有多强”，而是尽快让用户完成一次低成本创作。

更推荐的路径：

```text
说明能生成什么
-> 选择一个目标或模板
-> 给出可编辑示例 prompt
-> 生成一次结果
-> 保存/分享/继续编辑
```

不推荐的路径：

```text
连续介绍模型、素材、社区、会员、历史记录
-> 进入首页
-> 用户不知道第一步点哪里
```

AI 类产品还要注意：

- 示例 prompt 要降低空白输入压力。
- 结果页要有下一步，例如重新生成、编辑、保存、分享。
- 如果涉及会员或额度，先让用户理解价值，再出现付费或额度解释。
- 如果生成需要等待，等待状态本身也要被设计，不能只显示一个无信息 loading。

## 埋点与验证

引导页上线后，至少看这些指标：

- 首次核心动作完成率。
- 每一步曝光、下一步、跳过、流失。
- 权限授权率。
- 完成引导后的首个任务转化率。
- 次日/七日留存变化。
- 新用户是否更快到达第一次成果。

如果某一屏流失高，先问这屏是否太长、太抽象、太像广告、是否阻断了用户当前目标。

## 常见坏味道

- 把 onboarding 写成公司介绍。
- 把功能清单当成用户价值。
- 每一屏都有大量文案。
- 不给跳过入口。
- 看完引导后落到普通首页，没有下一步动作。
- 首次启动连续请求多个系统权限。
- 用户还没体验价值就弹订阅页。
- 为了掩盖复杂 UI，写很多教学文案，而不是改进 UI 本身。
- 引导状态只用一个布尔值，后续无法处理版本更新、重新展示和实验分组。
- 文案写死，后续多语言和 A/B 测试成本很高。
