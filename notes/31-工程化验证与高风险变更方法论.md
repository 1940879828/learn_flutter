# 31 工程化验证与高风险变更方法论

## 这份手册解决什么问题

Flutter 改动的风险不只来自 Dart 代码。代码生成、多语言、平台配置、Firebase、支付、广告、权限、数据库迁移和媒体能力，都可能需要不同验证门禁。

这份手册用于改动前判断风险级别，并选择最小但足够的验证组合。

## 什么时候使用

- 适合：任何准备提交的功能、修复、重构、配置变更、真实项目改动。
- 不适合：只读分析、不修改文件的调研。

## 一句话原则

验证要覆盖这次改动真正触达的边界，而不是机械只跑一个命令。

## 决策表

| 改动 | 验证 |
| --- | --- |
| docs-only | 链接、路径、Markdown、`git diff --check` |
| Dart 纯逻辑 | focused unit test + `fvm flutter analyze` |
| Widget UI | widget test 或手工验收 + analyze |
| 路由 | 进入、返回、缺参、redirect 手工路径 |
| model/codegen | build_runner + JSON roundtrip |
| l10n | 改 `.arb` + `fvm flutter gen-l10n` + 长文案检查 |
| 本地存储 | 重启恢复、迁移、清理、异常路径 |
| 权限/媒体 | 模拟器/真机验证 |
| 登录/支付/广告 | 测试账号、测试环境、完整回归 |
| App 初始化 | 冷启动、失败降级、白屏检查 |

## 固定检查问题

```text
这次改动触达了哪些边界：UI、状态、网络、存储、权限、平台、收入？
有没有生成文件需要由命令更新？
有没有真机才能验证的行为？
失败路径是否和成功路径一样被验证？
是否包含用户未授权的旧改动？
```

## Flutter 实现拆分

```text
Focused test
  针对本次行为的最小测试。

Project gate
  analyze / full test / build_runner / gen-l10n。

Manual path
  UI、路由、权限、媒体、登录等真实流程。

Risk review
  高风险模块改动后独立复查。
```

## 常见坏味道

- 只跑 analyzer，就认为功能没问题。
- 改 `.arb` 不跑 gen-l10n。
- 改 model 不跑 codegen 或 roundtrip。
- 权限、相册、视频只在模拟器看一眼。
- 登录/支付/广告改动没有测试账号和测试环境。
- 把第三方 warning 当成业务成功证据。
- 提交里混入无关文件。

## 验收标准

- 每类触达边界都有对应验证。
- focused test 或手工步骤能复现本次需求。
- 高风险模块列出残余风险。
- `git status` 中没有无关改动。
- 提交说明包含改动范围和验证证据。
