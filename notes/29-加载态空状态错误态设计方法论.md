# 29 加载态空状态错误态设计方法论

## 这份手册解决什么问题

很多页面失败不是因为主流程写错，而是 loading、empty、error、retry、stale 状态没设计。用户不知道系统在做什么，也不知道下一步能做什么。

这份手册用于把页面状态设计成完整体验，而不是只补一个转圈。

## 什么时候使用

- 适合：列表、详情、搜索、生成任务、图库、登录、保存、上传、下载。
- 不适合：瞬时本地计算或用户不会感知的内部状态。

## 一句话原则

每个非成功状态都要告诉用户：发生了什么、还能做什么。

## 决策表

| 状态 | UI 目标 | 常见动作 |
| --- | --- | --- |
| idle | 引导开始 | 输入、选择、创建 |
| loading | 说明正在处理 | 等待、取消 |
| refreshing | 保留旧内容 | 不打断使用 |
| empty | 给出下一步 | 创建、导入、搜索建议 |
| error | 解释失败并恢复 | 重试、去设置、换输入 |
| stale | 标记旧数据 | 刷新、继续查看 |
| success | 展示结果 | 保存、分享、继续 |
| canceled | 安静回到可操作状态 | 重新开始 |

## 固定检查问题

```text
用户第一次看到空页面时知道做什么吗？
loading 超过几秒是否需要更具体说明？
错误文案是否能指导下一步，而不是只说失败？
刷新时是否必须清空旧内容？
用户取消是否被误当成错误？
```

## Flutter 实现拆分

```text
State model
  明确 idle/loading/empty/error/success 等状态。

Page
  按状态切换主体内容。

Reusable local widgets
  在 feature 内沉淀空状态、错误态、重试按钮。

Repository / VM
  给出错误类型和恢复动作。
```

## 常见坏味道

- 首屏 loading 无限转，没有超时或错误。
- 空列表只写“暂无数据”，没有 CTA。
- 所有错误都显示“请求失败”。
- 刷新时清空整个页面，造成闪烁。
- 用户取消登录/选图被提示成错误。
- 错误态没有保留用户已输入内容。

## 验收标准

- 每个状态都有明确 UI 和用户动作。
- 空状态能推动用户进入核心任务。
- 错误能区分网络、权限、参数、业务失败。
- 重试不会重复创建昂贵任务。
- 文案进入多语言，按钮不会溢出。
