# 28 多语言与文案维护方法论

## 这份手册解决什么问题

多语言不是替换字符串。Flutter 项目里文案 key、`.arb`、placeholder、description、生成文件、布局长度和 fallback 都会影响功能质量。

这份手册用于新增或修改文案时，避免硬编码、漏翻译、手改生成文件和布局溢出。

## 什么时候使用

- 适合：新增按钮、弹窗、错误文案、引导页、权限说明、空状态、多语言页面。
- 不适合：debug-only 临时日志或不会展示给用户的内部字符串。

## 一句话原则

业务代码只依赖稳定 key，用户看到的文字由 `.arb` 和生成代码提供。

## 决策表

| 场景 | 做法 | 原因 |
| --- | --- | --- |
| 新增用户可见文案 | 改所有目标 `.arb` | 避免缺 key |
| 文案含变量 | 使用 placeholder | 适配不同语序 |
| 翻译需要语境 | 写 description | 降低误译 |
| 修改 `.arb` 后 | 跑 `fvm flutter gen-l10n` | 更新生成访问器 |
| 文案变长 | 检查布局 | 多语言可能溢出 |
| 临时 fallback | 明确退出条件 | 不长期依赖默认语言 |
| 生成文件 | 不手改 | 保持来源清晰 |

## 固定检查问题

```text
这段文案是否用户可见？
所有支持语言是否都补齐了 key？
变量是否需要 placeholder，而不是字符串拼接？
翻译者是否能从 description 理解语境？
长德语/葡萄牙语/西班牙语是否会撑爆布局？
```

## Flutter 实现拆分

```text
.arb source
  维护 key、文案、description、placeholder。

gen-l10n generated files
  提供类型安全访问器，不手改。

MaterialApp
  接入 delegates、supportedLocales、locale。

Widget
  使用 L.of(context).xxx，不硬编码用户文案。
```

## 常见坏味道

- 页面里直接写英文文案。
- 只改英文，其他语言缺 key。
- 用字符串拼接代替 placeholder。
- 手改 `localization_intl_*.dart`。
- 按英文长度设计按钮，其他语言溢出。
- 错误码、权限说明、订阅文案没有多语言。

## 验收标准

- 所有用户可见文案来自本地化系统。
- `.arb` key、placeholder、description 完整。
- 修改后生成文件来自命令。
- 至少检查一种长文案语言的布局。
- 缺翻译时有明确 fallback 策略。
