# 19 状态管理选型方法论

## 这份手册解决什么问题

写 Flutter 页面时，最常见的问题不是“不知道 Riverpod API”，而是不知道状态应该放在哪里。状态放太低会导致页面之间同步困难；状态放太高会让简单交互变重、重建范围变大、生命周期难收。

这份手册用于在动手前判断：用本地 `setState`，还是用 Riverpod 的 `Provider`、`NotifierProvider`、`FutureProvider`、`AsyncNotifierProvider`、`StreamProvider`。如果是在写插件、主题、表单上下文或底层 Scope，也要能识别 `InheritedWidget` / `InheritedNotifier` 这类 Flutter 原生下发机制。

## 什么时候使用

- 适合：新增页面状态、拆页面逻辑、处理远程数据、整理 provider、优化 rebuild 范围。
- 不适合：只改纯文案、纯样式、没有状态变化的静态 UI。

## 一句话原则

先按状态生命周期和副作用边界选位置，再按 API 便利性选 provider 类型。

## 决策表

| 场景 | 选择 | 原因 |
| --- | --- | --- |
| 只影响一个局部控件 | `StatefulWidget` / `setState` | 生命周期跟控件走，成本最低 |
| 从已有状态同步计算结果 | `Provider<T>` | 派生值不需要自己持有状态 |
| 注入 repository、api client、service | `Provider<T>` | 表达依赖来源，便于测试替换 |
| 一次性异步读取 | `FutureProvider<T>` | 自动表达 loading/error/data |
| 同步状态 + 多个 action | `NotifierProvider` | 状态和修改逻辑集中到 controller |
| 远程数据 + 刷新/重试/提交 | `AsyncNotifierProvider` | 异步状态和业务动作收口 |
| 持续推送的数据 | `StreamProvider<T>` | 适合登录状态、消息、下载进度 |
| 高频变化且只影响很小区域 | 局部 builder / `select` | 缩小 rebuild 范围 |
| 写插件、主题、表单上下文、底层 Scope | `InheritedWidget` / `InheritedNotifier` | 把基础设施对象下发给子树，避免层层传参 |

## 最小示例速查

### `StatefulWidget` / `setState`

适合只影响当前控件的小状态，例如按钮选中、展开收起、输入框本地状态。

```dart
class LikeButton extends StatefulWidget {
  const LikeButton({super.key});

  @override
  State<LikeButton> createState() => _LikeButtonState();
}

class _LikeButtonState extends State<LikeButton> {
  bool isLiked = false;

  @override
  Widget build(BuildContext context) {
    return IconButton(
      icon: Icon(isLiked ? Icons.favorite : Icons.favorite_border),
      onPressed: () {
        setState(() {
          isLiked = !isLiked;
        });
      },
    );
  }
}
```

判断点：如果这个 `isLiked` 离开当前 Widget 就没有意义，放本地最轻。

### `Provider<T>` 派生状态

适合从已有状态计算一个新结果，自己不持有可变状态。

```dart
final tasksProvider = Provider<List<String>>((ref) {
  return ['draft prompt', 'render image', 'save result'];
});

final taskCountProvider = Provider<int>((ref) {
  final tasks = ref.watch(tasksProvider);
  return tasks.length;
});
```

判断点：`taskCountProvider` 不需要单独修改，它只是跟着 `tasksProvider` 变化重新计算。

### `Provider<T>` 注入依赖

适合提供 repository、api client、service，方便页面读取，也方便测试替换。

```dart
final promptRepositoryProvider = Provider<PromptRepository>((ref) {
  return PromptRepository();
});

class PromptRepository {
  Future<List<String>> fetchRecentPrompts() async {
    return ['portrait', 'cyberpunk city'];
  }
}
```

判断点：这里的 provider 表达“依赖从哪里来”，不是表达 UI 状态。

### `FutureProvider<T>`

适合一次性异步读取，例如打开页面时加载一组数据。

```dart
final recentPromptsProvider = FutureProvider<List<String>>((ref) async {
  final repository = ref.watch(promptRepositoryProvider);
  return repository.fetchRecentPrompts();
});
```

页面读取时天然拿到 loading、error、data 三种状态。

```dart
final prompts = ref.watch(recentPromptsProvider);

return prompts.when(
  loading: () => const CircularProgressIndicator(),
  error: (error, stackTrace) => Text('加载失败：$error'),
  data: (items) => Text('最近 ${items.length} 条 prompt'),
);
```

判断点：如果只是“读一次并展示结果”，先考虑 `FutureProvider`。

### `NotifierProvider`

适合同步状态，并且有多个修改动作。

```dart
final counterProvider = NotifierProvider<CounterNotifier, int>(
  CounterNotifier.new,
);

class CounterNotifier extends Notifier<int> {
  @override
  int build() => 0;

  void increment() {
    state++;
  }

  void reset() {
    state = 0;
  }
}
```

页面里读状态、点按钮时调用 action。

```dart
final count = ref.watch(counterProvider);

return FilledButton(
  onPressed: () => ref.read(counterProvider.notifier).increment(),
  child: Text('count: $count'),
);
```

判断点：状态修改规则开始变多时，把 action 收进 notifier，比散落在 Widget 里更清楚。

### `AsyncNotifierProvider`

适合远程数据同时带刷新、重试、提交等动作。

```dart
final generationTasksProvider =
    AsyncNotifierProvider<GenerationTasksNotifier, List<String>>(
  GenerationTasksNotifier.new,
);

class GenerationTasksNotifier extends AsyncNotifier<List<String>> {
  @override
  Future<List<String>> build() async {
    return _fetchTasks();
  }

  Future<void> refresh() async {
    state = const AsyncLoading();
    state = await AsyncValue.guard(_fetchTasks);
  }

  Future<List<String>> _fetchTasks() async {
    final repository = ref.read(promptRepositoryProvider);
    return repository.fetchRecentPrompts();
  }
}
```

判断点：如果页面不仅要展示异步结果，还要把刷新、重试、提交逻辑收口，`AsyncNotifierProvider` 更合适。

### `StreamProvider<T>`

适合持续变化的数据，例如登录状态、消息流、上传/下载进度。

```dart
final downloadProgressProvider = StreamProvider<double>((ref) async* {
  for (var progress = 0.0; progress <= 1.0; progress += 0.25) {
    await Future<void>.delayed(const Duration(milliseconds: 300));
    yield progress;
  }
});
```

判断点：如果数据不是“请求一次结束”，而是不断推送新值，用 `StreamProvider` 更贴近真实模型。

### `select`

适合从一个较大的状态里只监听某个字段，减少不必要 rebuild。

```dart
final profileProvider = Provider<UserProfile>((ref) {
  return const UserProfile(name: 'Mia', credit: 12);
});

final credit = ref.watch(
  profileProvider.select((profile) => profile.credit),
);
```

```dart
class UserProfile {
  const UserProfile({required this.name, required this.credit});

  final String name;
  final int credit;
}
```

判断点：如果 UI 只关心 `credit`，就不要因为 `name` 变化也重建。

### `InheritedWidget` / `InheritedNotifier`

适合封装插件、主题、表单上下文、路由上下文这类“子树共享的基础设施对象”。它更像 Riverpod / Provider 背后的原生能力，不是日常业务状态管理的首选。

```dart
class KeyboardInsetsScope
    extends InheritedNotifier<KeyboardInsetsController> {
  const KeyboardInsetsScope({
    super.key,
    required KeyboardInsetsController controller,
    required super.child,
  }) : super(notifier: controller);

  static KeyboardInsetsController of(BuildContext context) {
    final scope = context
        .dependOnInheritedWidgetOfExactType<KeyboardInsetsScope>();
    return scope!.notifier!;
  }
}
```

判断点：如果你是在写一个底层组件，让整棵子树都能拿到同一个 controller，并且 controller 变化时依赖它的 Widget 要自动 rebuild，可以考虑 `InheritedNotifier`。如果只是普通页面业务状态，优先考虑 `setState`、`ValueNotifier` 或 Riverpod。

## 固定检查问题

```text
这个状态只服务一个 Widget，还是跨页面共享？
这个状态是同步状态，还是远程异步结果？
它有没有 action、刷新、重试、提交、取消？
页面退出时状态应该销毁还是保留？
状态变化会让多大的 UI rebuild？
```

## Flutter 实现拆分

```text
Widget
  只负责读取状态、展示 UI、把用户动作转成 callback。

Notifier / AsyncNotifier
  负责状态修改、刷新、提交、错误恢复。

Provider
  负责依赖注入和同步派生值。

InheritedWidget / InheritedNotifier
  负责把主题、插件 controller、表单上下文等基础设施对象下发给子树。

Repository / Service
  负责网络、本地存储、SDK 和业务边界。
```

## 常见坏味道

- 一个页面根部 `watch` 高频变化状态，导致整页重建。
- 简单按钮 hover、展开、tab 选择也上提成全局状态。
- Widget 里直接写网络请求、持久化、埋点和复杂业务分支。
- `read` 用在需要自动更新 UI 的地方。
- `watch` 用在按钮点击事件里，造成不必要订阅。
- 异步状态只用一个 `bool loading`，错误和空状态没有建模。
- 为普通业务页面手写 `InheritedWidget`，把本来可以用 Riverpod 或局部状态表达的逻辑做重。
- 写插件 Scope 时只暴露 controller，却没有明确哪些字段可监听、哪些字段只是同步读取。

## 验收标准

- 能说清每个状态的拥有者和生命周期。
- 能解释 `watch`、`read`、`listen` 的分工。
- 高频状态变化只重建必要区域。
- 远程数据有 loading、error、empty、data 和 retry。
- action 可以在 Notifier / AsyncNotifier 中单独测试。
