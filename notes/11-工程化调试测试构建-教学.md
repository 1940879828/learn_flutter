## 本章教学闭环

工程化不是“把所有命令都跑一遍”，而是知道每个命令守住什么边界。

```text
改依赖 / assets / fonts
→ pubspec.yaml
→ fvm flutter pub get
→ pubspec.lock

改 Dart 代码
→ fvm flutter analyze
→ focused test
→ fvm flutter test

改注解模型 / 生成链路
→ build_runner

改 .arb
→ gen-l10n
```

Web 前端可以类比：

- `pubspec.yaml` 像 `package.json`。
- `pubspec.lock` 像 lockfile。
- `flutter analyze` 像 `eslint + tsc` 的一部分。
- `flutter test` 像 unit test + component test。
- `build_runner` 像 Prisma/GraphQL/OpenAPI 代码生成。

## 第 1 步：先认识常用命令

常见命令是：

- `flutter pub get`
- `flutter analyze`
- `flutter test`
- `flutter run`

这些命令在日常开发里比“语法知识”更常用。

## 第 2 步：理解 FVM

FVM 的价值很简单：锁版本。

同一个项目，不同机器如果 Flutter 版本不一致，很容易出现依赖解析和代码生成差异。

## 第 3 步：理解代码生成

Flutter 生态里很多地方都依赖生成代码，比如：

- JSON 序列化
- 本地化
- 一些注解工具

这时就要记住 `build_runner`。

## 第 4 步：理解测试分层

你现在先记住三层：

- 单元测试
- widget test
- 集成测试

不是每个类都要测，但关键收口处要测。

## 第 5 步：理解调试流程

调试时你要会看：

- 控制台日志
- 断点
- 热重载
- 热重启

## 第 6 步：回到目标项目

优先读：

- `/Users/dev/Documents/Projects/flutter-spell-ai/pubspec.yaml`
- `/Users/dev/Documents/Projects/flutter-spell-ai/analysis_options.yaml`
- `/Users/dev/Documents/Projects/flutter-spell-ai/plugins/spellai_lint/`
- `/Users/dev/Documents/Projects/flutter-spell-ai/test/`

重点看：

1. 依赖和锁版本。
2. 自定义 lint。
3. 哪些地方用了生成代码。

本轮已观察到：

- SpellAI 使用 FVM 约束 Flutter `3.35.7`。
- 依赖中有私有 hosted package：例如 `turbo_duck_purchase`、`device_id`、`flutter_sse`、`sfml`、`arb_excel`。
- 依赖中有 git package：例如 `rive_rolls_collection`、`rive_rolls_graphics`、`rive_rolls_video_trimmer`。
- `analysis_options.yaml` 对目标项目更严格，尤其是返回类型、参数类型、throw 类型、相对 import、文件名等。
- `plugins/spellai_lint` 自定义规则要求函数和方法参数显式声明类型，不能照学习 demo 里较宽松的匿名参数风格直接迁移。
- `*.g.dart` 和多语言生成文件属于生成产物，通常通过命令更新，不手工编辑。

第一次改 SpellAI 前，建议先只跑 focused 路径；如果依赖环境不完整，把缺失项记录清楚，不要用跳过门禁掩盖问题。

## QA 问答

### Q1：为什么要用 FVM？
因为 Flutter 版本一乱，问题就很难定位。

### Q2：`flutter analyze` 和 `flutter test` 差在哪？
一个看静态问题，一个看运行行为。

### Q3：什么改动前要特别谨慎？
涉及权限、路由、数据模型、支付、媒体和平台原生配置的改动。

### Q4：为什么 widget test 很有价值？
它能把 UI 行为固定下来，防止回归。

### Q5：什么时候该先写测试再改代码？
当你在改一个有明确行为和回归风险的模块时。
